## Context

Explored the full data architecture across all databases:
- **HOSPITAL360_CUR**: 28 tables across 6 schemas (CLINICAL, FINANCIAL, OPERATIONS, GOVERNANCE, POPULATION_HEALTH, SUPPLY_CHAIN, WORKFORCE)
- **HOSPITAL360_ML**: 11 tables across 3 schemas (FEATURES, MONITORING, PREDICTIONS)
- **HOSPITAL360_RAW / HOSPITAL360_INT**: Empty (data loaded directly to CUR for this demo)

The data model is a classic star schema with conformed dimensions (DIM_PATIENT, DIM_PROVIDER, DIM_FACILITY, DIM_PAYER, DIM_DRG) joined to fact tables (FCT_ENCOUNTER, FCT_REFERRAL, FCT_OR_CASE, FCT_CLAIM_LINE) and pre-built analytical marts (MART_READMISSION_LOS, MART_PATIENT_LEAKAGE, MART_OR_CAPACITY, MART_DENIALS_REVCYCLE).

Here's the content per page:

### 1. Provider 360 Dashboard
- **Sources**: Epic ADT (encounters), Epic Referrals, Epic OpTime (OR), Epic Claims/Remittances
- **Tables**: `FCT_ENCOUNTER` (200K encounters) joined to `DIM_FACILITY`, `DIM_PAYER`, all 4 marts aggregated for KPIs
- **Joins**: Each mart is pre-joined (denormalized). KPIs query marts directly with facility/date filters.

### 2. Readmission & LOS
- **Sources**: Epic ADT (admits/discharges), Epic DRG Grouper, Epic Claims (charges/costs), CMS MS-DRG reference
- **Tables**: `MART_READMISSION_LOS` — pre-joined encounter-level table
- **Joins**: `FCT_ENCOUNTER` JOIN `DIM_PATIENT` (demographics, HCC score) JOIN `DIM_DRG` (DRG weight, expected LOS) JOIN `DIM_PAYER` (payer type/name) JOIN `DIM_FACILITY` + `DIM_DEPARTMENT`. 30-day readmission flag computed via window function (LEAD on patient admit dates).

### 3. Patient Leakage
- **Sources**: Epic Referral Management, Epic Provider Directory, Epic Scheduling
- **Tables**: `MART_PATIENT_LEAKAGE` — referral-level detail
- **Joins**: `FCT_REFERRAL` JOIN `DIM_PATIENT` (demographics, payer) JOIN `DIM_PROVIDER` (referring provider, specialty) JOIN `DIM_FACILITY`. Leakage flag = referral status indicates out-of-network completion. Revenue estimated from specialty-level averages.

### 4. OR Capacity
- **Sources**: Epic OpTime (surgical scheduling), Epic Block Management, Epic Surgeon Preference Cards
- **Tables**: `MART_OR_CAPACITY` — case-level with utilization
- **Joins**: `FCT_OR_CASE` JOIN `DIM_PROVIDER` (surgeon name/specialty) JOIN `DIM_FACILITY` JOIN `DIM_PROCEDURE_CPT` (CPT code/description). Utilization = case_minutes / block_minutes. Delay = actual_start - scheduled_start.

### 5. Denials & RevCycle
- **Sources**: Epic Claims (professional/institutional), Payer Remittances (835), Epic Appeals Workflow
- **Tables**: `MART_DENIALS_REVCYCLE` — denied claim lines
- **Joins**: `FCT_CLAIM_LINE` (denied_flag=TRUE) JOIN `DIM_PAYER` (payer type, timely filing limit) JOIN `DIM_PROVIDER` JOIN `DIM_DIAGNOSIS_ICD10` JOIN `DIM_PROCEDURE_CPT`. Denial categorization derived from DENIAL_REASON mapping. Estimated recovery = allowed_amt * appeal success probability.

### 6. ML Insights
- **Sources**: Cortex ML functions operating on CUR-layer marts
- **Tables**: `PRED_ENCOUNTER_VOLUME` (FORECAST), `PRED_DENIAL_ANOMALIES` (DETECT_ANOMALIES), `PRED_READMISSION_DRIVERS` / `PRED_LEAKAGE_DRIVERS` (CONTRIBUTION_EXPLORER)
- **Joins**: Feature views (`VW_DAILY_ENCOUNTER_VOLUME`, `VW_DAILY_DENIAL_VOLUME`) aggregate fact tables by date. Models read feature views → write predictions tables. No complex joins at query time — predictions are pre-computed.

### 7. Cortex Analyst
- **Sources**: All CUR-layer tables exposed via Semantic View
- **Tables**: Queries any of the 4 marts + fact/dimension tables
- **Joins**: Defined in the Semantic View DDL (`HOSPITAL360_APP.SEMANTIC_VIEWS.HOSPITAL360_ANALYTICS`). The semantic view declares relationships and Cortex Analyst generates JOINs automatically based on the natural-language question.

### 8. Cortex Agent
- **Sources**: Same as Cortex Analyst (calls Analyst as a tool)
- **Tables**: All accessible via the agent's tool calls to Cortex Analyst
- **Joins**: Agent orchestrates multiple Analyst queries and synthesizes across domains. Can chain queries across different marts in a single answer.

### 9. Ops Monitor
- **Sources**: Snowflake INFORMATION_SCHEMA (tasks, tables), `HOSPITAL360_ML.MONITORING` tables
- **Tables**: `PIPELINE_RUN_LOG`, `DATA_QUALITY_CHECKS`, `MODEL_PERFORMANCE_LOG`, plus `INFORMATION_SCHEMA.TASK_DEPENDENTS`, `INFORMATION_SCHEMA.TABLES`
- **Joins**: Monitoring tables are standalone (no star-schema joins). Task DAG uses `TABLE(HOSPITAL360_ML.INFORMATION_SCHEMA.TASK_DEPENDENTS(...))` table function for dependency graph.
